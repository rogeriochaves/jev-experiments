Jev on the Bench

Jev answers typed questions about a piece of text and returns probabilities instead of text. This page measures how fast one request is, how much text fits in one request, how many requests run at once, what a job over 100k traces costs, and whether the same model can be pushed into writing sentences and code.

Latency

How fast is one request

A request with a 1k-token conversation and one yes/no question comes back in about 275 ms. Sending a 13k-token conversation instead adds 50 ms, and a 24k-token one adds 150 ms, so input size only starts to matter above 10k tokens. Adding questions costs even less: 50 questions on the same text come back in the same time as one.

Each point is the median of five requests sent one at a time from Amsterdam, and about 100 ms of every number is network time.

Concurrency

How many requests can run at once

Each test sends a batch of requests while keeping a fixed number of them in flight, from 8 up to 512. A single request carries one conversation of about 1.9k tokens and three yes/no questions. A packed request carries ten conversations and thirty questions, which is close to the ceiling, because twelve conversations is the most that fit under the 32k-token limit on one request.

With single requests, throughput kept climbing to 160 requests/s and 470k tokens/s at 512 in flight without a single 429. With packed requests the API started returning 429 at 64 in flight, around 340k tokens/s. The cost of more in-flight requests is latency: the median went from 270 ms at 8 in flight to 2 s at 512, because requests wait in a queue on their side.

Sustained

What throughput holds for a full minute

This run kept 256 single requests in flight for 60 seconds. For the first 10 seconds the API accepted 480k tokens/s and 163 requests/s with no 429s. After that it settled at 315k tokens/s and 108 requests/s, and every request above that rate came back as a 429, which the client retried with backoff.

Plan a batch job around the 315k figure. It is above the 250k tokens/s in the docs, and the docs also say the limits change without notice. The two small bars after the 60 s mark are retries finishing.

Limits

How much fits in one request

Large question counts do cost time: 400 questions answered in 2.8 s, 1000 in 6.7 s and 2000 in 13.7 s, measured while other benchmarks were running. The 255-option limit is a validation error, not a soft limit, so the caveman vocabulary below has exactly 255 entries.

Cost

What it costs to judge 100k traces

Send one request per trace with as many questions as you need, and keep the client at the steady rate measured above. Two limits apply at the same time, tokens per second and requests per second, and the slower of the two decides the wall time. For 100k traces of 1.9k tokens the requests/s limit is the slower one, so packing two traces per request would cut the time from 15 to 12 minutes. Change the sliders to match your traces.

Accuracy

How accurate is it as a judge

The test set is 300 support conversations written by gpt-5-mini with the label given in the prompt: 75 where the customer complains openly, 75 where the customer is annoyed without saying so (short replies, "as I said", asking for a human), 75 neutral and 75 satisfied. The question for every method is the same: is the customer annoyed at any point.

Jev answered it three ways: a yes/no question with one conversation per request, a four-way choice with one conversation per request, and the same yes/no question with eight conversations packed into each request. gpt-5-mini answered the same question in JSON mode as the baseline.

Packing eight conversations into one request saved 23% of the tokens and lost 11 points of accuracy, because the answer for one conversation picks up signal from the conversations next to it. The TypeSafe docs warn that unrelated text in the state lowers accuracy, and here it happened on a 25k-token request. So pack only when cost matters more than accuracy.

With one conversation per request, raising the yes threshold from 0.5 to 0.7 fixes the six false positives and gives 100% on this set. On the four-way choice Jev separated open complaints from subtle annoyance on all 150, and labelled 38 of the 75 neutral conversations as satisfied. The neutral prompt asked for a calm conversation that proceeds normally, and a calm conversation where the agent fixes the problem reads as satisfied, so those two labels overlap by construction.

Text generation

cavejev: can Jev write sentences

Jev cannot output text, but a Choice question returns a probability for every option, so a loop can ask "which word comes next" with all 255 caveman words as options and sample the next word from those probabilities. The sampler uses the same controls as a normal language model decoder: temperature, top-k, top-p, a repetition penalty, frequency and presence penalties, no repeated trigrams, and no word twice in a row.

Without those controls, greedy decoding repeats itself after a few words, for example "do light do light do light do light" on the question about the sky. The samples below use the full sampler. There are three modes. The parallel mode predicts every word slot at once and re-predicts the least confident slots for six rounds. The hier mode asks for the word class and then the word inside that class, in one request per word. The seq mode asks one flat 255-way Choice per word.

go run ./cmd/cavejev -mode hier "Why is the sky blue?"

Why hier mode gives better sentences

With all 255 words in one Choice, the top word only gets 5 to 28% of the probability, so sampling picks from many near-equal words and the sentence drifts. The hier mode sends five questions in one request: which word class comes next (noun, verb, adjective, function word or punctuation), and for each class, which word. Multiplying the class probability by the word probability gives one word with 60 to 74% at each step. Code generation

codejev: can Jev write code that runs

The generator writes JavaScript one grammar step at a time. It keeps the code so far and a stack of what still has to be written, and at each cursor position it asks Jev to choose only among the options that are valid there: which kind of statement, which kind of expression, which operator, which variable in scope, which builtin function. Because every option is valid, the output always parses, so there is no need to check compilation and push back.

One request resolves a whole node, because it carries the main question plus the follow-up questions for every branch, and the code reads only the answers it needs. Variable names come from caveman nouns. Each of the 16 tasks got six attempts: the first with greedy decoding, the other five sampled at temperature 0.6. A node script then runs each program against three tests.

Method and caveats

Caveats

All code is Go, calling POST /v1/systemone over plain HTTP from one process on a laptop in Amsterdam, so every latency includes about 100 ms of network. The client retries 429 and 5xx responses with exponential backoff and respects the Retry-After header.

The rate limits change. The TypeSafe models page says they adjust without notice while capacity grows, so the 315k tokens/s steady rate and the 480k burst are what this key got on 2026-09-17.

Some runs overlapped. The limits probe and part of codejev ran while another benchmark was at full load, which inflates a few of their latencies (the 1000-question request at 6.7 s, the packed probe at 14 s). The latency chart ran alone.

The dataset is synthetic. gpt-5-mini wrote the conversations with the label in the prompt, so the labels are clean but the text is not production traffic. The neutral versus satisfied confusion comes from how the labels were defined.

Packing trades accuracy for cost. On this data it cut cost by 23% and accuracy by 11 points at eight conversations per request. For a judging job, send one trace per request with many questions, since questions add almost nothing to latency or cost.

Text generation is a stunt. Sequential mode runs at 3 words/s and produces word salad with an occasional readable sentence. Hier mode answers questions in short caveman sentences at 2.5 words/s for about half a cent per reply. Mask-predict is the fastest at 4 s per reply and the most expensive, because every slot repeats the 255-option list.

Code generation did better than text. Greedy decoding solves 9 of 16 tasks and best-of-6 solves 12, for $0.055 across 96 programs. The factorial miss comes from the grammar offering only < as a loop bound, and the array tasks fail because the grammar has no spread operator.
